# План імплементації — media-library

Документ описує, як реалізується `spec.md`. Порядок фаз підібраний так, щоб робочий наскрізний сценарій (зберегти → знайти → відкрити) з'явився якомога раніше, а важкі модальності додавалися до вже працюючого каркаса.

---

## 1. Архітектура

Один процес Python. FastAPI піднімається на `127.0.0.1` на випадковому вільному порту, `pywebview` відкриває системне вебв'ю на цю адресу. Фронтенд — зібраний React-бандл, який backend роздає як статику. Жодного Electron, жодного Rust, жодного міжмовного IPC: фронт спілкується з беком звичайним HTTP.

Важка обробка (ASR, ембедінги, нарізка кадрів) виконується у фоновому воркері з чергою задач, а не в HTTP-обробнику. Інакше вебв'ю блокується на хвилини при першому ж відео.

```
┌──────────────── pywebview (системне вебв'ю) ────────────────┐
│  React + Tailwind                                           │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP (127.0.0.1)
┌───────────────────────────┴─────────────────────────────────┐
│  FastAPI                                                    │
│    api/          items · search · tags · jobs · media       │
│    ingest/       image · video · audio · text               │
│    search/       query · fusion (нормалізація оцінок)       │
│    ml/           registry (лінива загрузка, вибір девайса)  │
│    worker/       черга задач, прогрес, ретраї               │
└───────────────────────────┬─────────────────────────────────┘
                            │
              SQLite + sqlite-vec (один файл)
              data/originals · data/frames · data/thumbs
```

## 2. Модель даних

```sql
items(
  id, kind,                    -- image | video | audio | text
  label,                       -- детермінований дефолт, редагований
  created_at,                  -- дата створення оригіналу (для фільтра)
  added_at,
  stored_path, source_path, mime, size_bytes,
  duration_s, width, height,   -- NULL там, де не застосовно
  text_content,                -- для kind=text
  transcript, transcript_lang, -- для audio/video
  transcript_edited,           -- чи правив юзер
  status                       -- pending | processing | ready | failed
)

tags(id, name UNIQUE)          -- керований словник з адмінки
item_tags(item_id, tag_id)
frames(id, item_id, ts_s, path)

embeddings(id, item_id, frame_id, space, vec_rowid)
vec_image  -- virtual table vec0, простір зображень
vec_text   -- virtual table vec0, простір текстів

jobs(id, item_id, type, status, progress, error, created_at, updated_at)
```

Ключове рішення: **вектори не лежать в `items`**. Один запис може мати багато векторів (відео — кадри плюс транскрибція), тому зв'язок іде через `embeddings` із явним полем `space`.

`created_at` береться з метаданих файлу (EXIF для фото, контейнер для відео), з відкатом на mtime.

## 3. Пошук і ранжування

1. Текст запиту кодується **двічі** — текстовим енкодером мультимодальної моделі та текстовим ембедером.
2. kNN по `vec_image` і по `vec_text` окремо, з надлишком (кожен ~200 кандидатів).
3. Фільтри (тип, дата, теги) застосовуються до множини id.
4. **Нормалізація в межах кожної модальності** — див. нижче.
5. Злиття: групуємо по `item_id`, беремо максимум по записах одного item (відео, що збіглося і кадром, і транскрибцією, не має з'являтися двічі), сортуємо.

### Нормалізація

Косинусні схожості у двох різних просторах мають різні масштаби й різні базові рівні: 0.7 у CLIP-просторі і 0.7 у E5-просторі означають зовсім різне. Просто злити їх в один список — отримати рейтинг, у якому одна модальність систематично давить іншу.

- **v1 (min-max у межах видачі).** Просто й швидко, але має відому ваду: найкращий результат завжди показує 100%, навіть коли насправді нічого не знайшлося.
- **Цільовий варіант (калібрування).** Одноразово рахуємо розподіл схожостей на випадкових парах запит–запис у кожному просторі, зберігаємо середнє й дисперсію, і переводимо сиру схожість у z-оцінку, а тоді сигмоїдою — у відсоток. Тоді «87%» означає одне й те саме для картинки й для транскрибції, а низька релевантність чесно показується як низька.

Друге реалізується у Фазі 9; до того живе перше.

## 4. Фази

### Фаза 0 — Спайк: перевірка ризикових припущень

Ця фаза йде першою саме тому, що три речі нижче можуть змінити весь план, і дізнаватися про це на Фазі 7 було б дорого.

- **`sqlite-vec` на Windows.** Це завантажуване розширення SQLite, і його треба вміти підвантажити з Python (`enable_load_extension`). Перевірити, що збірка CPython у цьому оточенні це дозволяє. Якщо ні — запасний варіант: LanceDB (теж вбудована, без сервера) або FAISS з окремим файлом індексу.
- **Вибір мультимодальної моделі.** Зібрати ~30 тестових пар «запит українською → очікувана картинка» і заміряти на двох кандидатах: `jina-clip-v2` (сильніша, але важча; **обов'язково перевірити ліцензію** — вона може бути обмежена некомерційним використанням) і `clip-ViT-B-32-multilingual-v1` (легша, ліберальніша ліцензія). Обрати за результатом заміру, а не за описом.
- **Розмір моделі ASR.** Заміряти `faster-whisper` на 4060 і на CPU: `large-v3-turbo` проти `medium` проти `small`, на реальному файлі кожною з трьох мов. Результат — дефолт у налаштуваннях і чесна оцінка «скільки чекати на годину відео».

Вихід фази: три ухвалені рішення, зафіксовані в цьому документі.

#### Результати спайку

**`sqlite-vec` — працює.** SQLite 3.50.4, `enable_load_extension` доступний, `sqlite_vec 0.1.9` вантажиться, kNN і фільтрація по `rowid IN (...)` разом із `MATCH` теж працюють. Запасний варіант із LanceDB не потрібен. Одна пастка, на яку вже наступили: `vec0` не бачить `LIMIT`, переданий як параметр — потрібен явний `k = ?`.

**Python 3.14 — працює.** Колеса під `cp314` є в усіх ключових пакетів: `torch 2.14.0`, `ctranslate2 4.8.2`, `onnxruntime 1.30.0`, `transformers 5.17.0`. Відкочуватися на 3.12 не потрібно.

**Залізо:** RTX 4060 Laptop, 8 ГБ VRAM. Це ноутбучна версія — обмеження по пам'яті реальне й впливає на вибір моделі ASR.

**Замір моделей — очікує тестові файли.** Потрібні зразки реального контенту (див. розділ 7).

### Рішення по збірці (ухвалено до Фази 12)

Вимога «на виході exe» ухвалена з самого початку, тому ML-шар проєктується під неї, а не підганяється потім.

- **У збірку не входить `torch`.** Розпізнавання мовлення йде через CTranslate2 (`faster-whisper`), ембедінги — через ONNX Runtime. `torch` лишається залежністю розробки: ним експортуються моделі в ONNX.
- **Ваги вшиваються у збірку.** Інсталятор повністю офлайновий, інтернет не потрібен ніколи.
- **Наслідок:** підсумковий розмір ~2-4 ГБ (застосунок + ваги) замість 6-9 ГБ на torch-шляху. Ціна — кожен гігабайт у вагах тепер коштує, тож на заміру моделей розмір є критерієм нарівні з якістю.
- **Обмеження, яке з цього випливає:** кандидати на Фазі 0 звужуються до моделей, які реально експортуються в ONNX. Якщо найкраща за якістю модель не експортується — беремо наступну.
- **Відкрите питання (вирішиться заміром):** GPU-прискорення потребує CUDA/cuDNN-бібліотек, а це ще гігабайти у збірці. Якщо CPU-режим на int8 дасть прийнятну швидкість — GPU зі збірки викидається, і застосунок сильно легшає.

### Фаза 1 — Каркас

`pyproject.toml`, FastAPI, збірка фронта, `pywebview` відкриває вікно, ендпоінт здоров'я. Вікно відкривається й показує React — далі все нарощується всередині.

### Фаза 2 — Сховище

Схема, міграції, підключення з підвантаженням `sqlite-vec`, шар доступу до даних, створення тек `data/`.

### Фаза 3 — Картинки наскрізно

Копіювання в бібліотеку, дедуплікація по хешу вмісту, thumbnail, ембедінг, запис у `vec_image`. Екран додавання з drag-and-drop.

### Фаза 4 — Пошук v1

Тільки картинки, тільки min-max нормалізація, без фільтрів. **Перший момент, коли застосунок робить щось корисне наскрізно.**

### Фаза 5 — Текст

Вставлений текст і `.txt`/`.md`. Лейбл із перших ~8 слів. Довгі тексти ріжуться на фрагменти з перекриттям — інакше ембедінг сторінки тексту розмивається в середнє й перестає шукатися.

### Фаза 6 — Аудіо

Черга фонових задач із прогресом, `faster-whisper` з обмеженням мов до uk/ru/de, екран редагування транскрипції, переембедінг після правки. Тут же — сценарії помилок: модель не завантажилася, файл битий, мова не розпізналася.

### Фаза 7 — Відео

Те саме, що аудіо, плюс відбір кадрів по зміні сцени з жорстким лімітом (дефолт — до 12 на відео) і мінімальним інтервалом між кадрами. Кадри йдуть у `vec_image` тим самим шляхом, що й звичайні картинки.

### Фаза 8 — Теги й фільтри

Адмінка словника тегів (додати / перейменувати / видалити, з показом кількості використань перед видаленням). Проставляння тегів на записі — вибір зі списку, без створення довільних. Фільтри у пошуку: тип, діапазон дат, теги.

### Фаза 9 — Калібрування ранжування

Заміна min-max на калібровані відсотки (розділ 3).

### Фаза 10 — Перегляд

Повноекранний перегляд картинки, програвач відео й аудіо з перемоткою до моменту збігу кадру, читалка тексту з підсвіченим фрагментом.

### Фаза 11 — Дизайн

Полірування: темна тема, сітка результатів, стани порожнечі й завантаження, клавіатурні скорочення.

### Фаза 12 — Пакування

Збірка в застосунок, екран першого запуску із завантаженням ваг моделей (з прогресом — там гігабайти), бандлінг `ffmpeg`.

## 5. Ризики

| Ризик | Наслідок | Що робимо |
|---|---|---|
| `sqlite-vec` не підвантажується на Windows | Міняється весь шар зберігання векторів | Фаза 0; запасний варіант — LanceDB |
| Ліцензія `jina-clip-v2` обмежує використання | Гірша якість пошуку на другій моделі | Фаза 0; перевірити до того, як зав'язуватися |
| Розмір збірки з `torch` — кілька ГБ | Важкий інсталятор | Прийняти як даність або лишити запуск із venv замість інсталятора |
| ASR повільний на довгих відео | Незручно, але не блокує | Фонова черга з самого початку (Фаза 6), не доробка потім |
| Якість ASR українською нижча за очікувану | Пошук по відео слабший | Поле транскрибції редаговане за спекою — юзер править, ембедінг перераховується |

## 6. Припущення

Зафіксовані тут, бо спека їх прямо не визначає. Якщо якесь не так — скажи, це змінює обсяг робіт.

1. **Масштаб** — десятки тисяч записів, не мільйони. Тому повний перебір векторів у SQLite прийнятний і ANN-індекс не потрібен.
2. **Один користувач, одна бібліотека**, одна машина. Ні синхронізації, ні багатокористувацького доступу.
3. **Дедуплікація** — повторне додавання того ж файлу впізнається по хешу вмісту і не створює другий запис.
4. **«Перші N слів»** у картці результату — 25, налаштовується.
5. **Редагування транскрипції** запускає переембедінг цього запису.
6. **Видалення запису** видаляє й скопійований оригінал із бібліотеки, з підтвердженням.
7. **Мова інтерфейсу** — українська, без перемикача.
8. **Мережа** потрібна лише для одноразового завантаження ваг моделей; далі застосунок працює офлайн.

## 7. Що потрібно від тебе

**Тестові файли для заміру моделей (Фаза 0).** Поклади у `samples/` кілька зразків свого реального контенту:

- `samples/audio/` — по одному аудіо чи короткому відео українською, російською та німецькою, бажано хвилини на 2-5. Саме реальний запис, а не студійна начитка: якість ASR на реальному звуці й на чистому відрізняється сильно.
- `samples/images/` — 20-30 картинок, схожих на те, що ти реально складатимеш у бібліотеку.
- `samples/queries.txt` — рядки виду `запит українською | очікуване_ім'я_файлу.jpg`, по одному на рядок. Це і є мірка, за якою обирається модель пошуку по картинках.

Без цього замір робиться на синтетиці, а вона систематично лестить моделям і веде до неправильного вибору.
